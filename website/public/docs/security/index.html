Security model

The sandbox is the boundary. Agents run with their own approvals on auto, so what keeps them in check is what the sandbox lets them reach, not a prompt asking "may I?" before every command.

The sandbox

Every session runs in a sandbox: bubblewrap and seccomp on Linux, Seatbelt on macOS, through Anthropic's sandbox-runtime at a pinned version. A session:

  • can write only its workspace, its temp folder, its agent's own state and a shared tools folder where agents install helpers for themselves, never into your home folder;
  • cannot read secrets folders, other agents' credentials or the host's data;
  • has no network except the host's per-session proxy, which allows only the agent's provider plus the workspace's network profile, resolves names itself and refuses private addresses.

Each agent gets a configuration the host controls, with none of your personal MCP servers, hooks or plugins. Nothing from the repository, such as its git hooks, runs outside the sandbox.

Leaving the sandbox, with your approval

Anything that needs your credentials goes through the host, which shows you what will run and waits for you, on the desktop or your phone.

WhatHow it is handled
MCP connectorsReached only through the host's gateway, which holds the credentials and asks before write tools by default.
Installing a tool on your computerYou see the exact command and the agent's reason. It runs as you only after you approve: a registry package and plain version, no shell, one at a time, logged.
PushingThe sandbox can't read your git credentials. The host asks you to approve the exact git push and runs it for the agent. Fetching runs without asking.
Pull requestsOpened with your GitHub CLI after you approve the title and description.
Any other command that needs your loginsYou see the exact argument list and its input. The host runs it as you in the session's folder after you approve, never through a shell.

"Always Allow" lets a command prefix such as gh pr edit run without asking from then on. These are listed, and undone, under Settings → Connectors. Shells, interpreters and build tools always ask.

Your own terminal

The desktop app's terminal is a login shell the host runs as you, outside every sandbox, exactly as a terminal window would be. It is yours, not an agent's.

WhoWhat they get
The app on the host's own computerTerminals, over the local socket.
A paired phone or desktopNone. Every terminal method needs the admin capability, which paired devices never hold; they hear nothing about your terminals.
AgentsNone. A session can't connect to the host's socket, and the gateway offers no terminal tool.

Opening and closing a terminal is written to the audit log. What you type and what it prints are not logged.

Remote access and the relay

The host listens on no network port. Local clients use a Unix socket, and the host dials out to the relay. Phones and the host talk through the relay over end-to-end Noise tunnels (XXpsk3 to pair, IK afterwards), so the relay forwards ciphertext it cannot read.

The one exception is webhook ingress, which the relay seals to the host in memory as it arrives. So the owner of the Cloudflare account the relay runs on, which is you, could see webhook contents and nothing else.

Push notifications

Notifications go from the host to the relay, which passes them to Apple. Their content is sealed with a key each phone gives the host (ChaCha20-Poly1305) and opened on the phone, so Apple and the relay see only a generic alert. The phone's notification token goes to the relay, never to the host.

Limits and reporting

AgentOS is early software. docs/status.md records what has been verified, how, and on which platforms, including the sandbox escape test suite.

Found a vulnerability? Please report it privately, as described in SECURITY.md.
